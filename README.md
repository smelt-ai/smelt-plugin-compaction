# 压缩调优

[smelt](https://github.com/smelt-ai/smelt) 的面板插件：按你自己的用法，给 Pi 和 Claude Code 的每个模型算出最省的自动压缩点。

Pi 默认在「上下文窗口 − 16384」时才压缩，1M 窗口的模型要到 98% 才动手。那时每次调用都要把将近一百万 token 读一遍，压缩时还得把八十多万 token 交给模型写摘要，又慢又贵。早一点压缩又会多出摘要和返工的开销。哪个点最划算，取决于你的对话怎么长、压缩后要读回多少东西，只能拿你自己的记录算。

## 它做什么

1. 读你的全部会话，取出每次模型调用的 usage（输入、缓存读写、输出，Pi 还有费用）和每次压缩：
   - Pi：`~/.pi/agent/sessions/**/*.jsonl`；
   - Claude Code：`~/.claude/projects/**/*.jsonl`（含子代理）。一次回复拆成几行写，按 `requestId` 只算一次；压缩记录里有耗时。
2. 对每个模型、每个候选压缩点，把你这段时间的对话按原样重放一遍，算出总成本，挑最省的。细节见下面的「调优原理」。
3. 界面上每个模型一张卡片：现在在哪压缩、建议在哪、能省多少、压缩次数怎么变、成本曲线、你的用法统计。

点「采用」把建议写进 agent 自己的设置，新开的会话生效；「撤销」删掉这一项；你自己给某个模型设过的值，插件不改。

**Pi** 写 `~/.pi/agent/settings.json`：

```json
{ "compaction": { "modelOverrides": { "provider/model": { "reserveTokens": 744000 } } } }
```

Pi 在上下文超过「窗口 − reserveTokens」时压缩，所以 1M 窗口写 744000 就是在 25.6 万时压缩。写入时和 Pi 用同一把锁（`settings.json.lock`）。

**Claude Code** 写 `~/.claude/settings.json`：

```json
{ "modelSettings": { "claude-opus-5-5": { "autoCompactWindow": 290000 } } }
```

Claude Code 在「autoCompactWindow 和模型窗口取小，再减约 3.3 万」时压缩，取值 10 万到 100 万。环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 盖过设置文件，设了它插件就不写。会话里没记模型窗口，用过超过 200K 的提示词就按 1M 算。没设时 Claude Code 用它自己给模型调的窗口，插件按你压缩过的位置推算现在的压缩点。

## 调优原理

代码在 `engine/tune.js`，算法移植自 [magpie](https://github.com/yetone/magpie) 的 `internal/tune`（MIT，见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)）。

### 要权衡的是什么

agent 每调用一次模型，都要把整段上下文重新发一遍。有提示词缓存时，旧的部分按缓存读计价（大约普通输入的十分之一），新加的部分按缓存写计价，但上下文越长，每一次调用的底价就越高。

压缩能把上下文砍短，但它本身有一笔固定开销：
- 把整段上下文读一遍，交给模型写摘要；
- 摘要是模型的输出，输出比输入贵得多；
- 下一次调用要把摘要写进缓存；
- 摘要会漏掉一些文件内容和工具结果，agent 接下来要重新读回来（下面叫「返工」）。

压得晚，每次调用都在读很长的上下文；压得早，这笔固定开销付得更频繁。总成本随压缩点先降后升，中间有一个最低点。最低点在哪，取决于你的对话每次涨多少、压缩后剩多少、返工多少、这个模型各类 token 的价钱，所以只能拿你自己的记录来算。

举个例子：每次调用涨 5000，压缩后剩 4 万。在 98 万时压缩，平均每次调用要读约 50 万；在 25 万时压缩，平均只读约 14 万，代价是每四十多次调用压缩一次。

### 第一步：从你的会话里量出几个数

每个会话文件是一段对话，里面的调用按时间排好。一次调用的「提示词」是输入、缓存读、缓存写三项之和。

| 量 | 怎么算 |
|---|---|
| 每次增长 | 相邻两次调用提示词之差的中位数。压缩和回退造成的下降不算 |
| 开头 | 每段对话第一次调用的提示词（系统提示、工具定义）的中位数，压缩会保留这部分 |
| 压缩前 / 压缩后 | 每次压缩前最后一次调用、压缩后第一次调用的提示词，各取中位数 |
| 返工 | 每次压缩后数 10 次调用，看提示词比「按这段对话平时的增长」多涨了多少（不到 0 记 0），取中位数 |
| 压缩耗时 | 每次压缩让人等了多久的中位数，至少量到 3 次才用 |

数据不够时的补充：
- 一次压缩都没见过：假设压缩后比开头多 1 万；
- 见过的压缩少于 5 次：返工至少按 1 万算。

哪里发生了压缩，直接读会话里的压缩记录（Pi 的 `compaction`、Claude Code 的 `compact_boundary`）。magpie 原版靠「提示词骤降到不足 60%」去猜，回退、分叉也会被当成压缩；这里不会。

### 第二步：重放

对每个候选压缩点 T，把每段对话从第一次调用开始重放：

```
摘要 = 压缩后 − 开头
上下文 = 第一次调用的提示词
成本 += 上下文 × 写 + 第一次的输出 × 出

之后每一次调用：
  增长 = 这次的提示词 − 上次的提示词（是压缩或回退就记 0）
  如果 上下文 + 增长 > T，且 上下文 > 压缩后：
    成本 += 上下文 × 读 + 摘要 × 出 + (摘要 + 返工) × 写   ← 一次压缩
    上下文 = 压缩后 + 返工
  成本 += 上下文 × 读 + 增长 × 写 + 这次的输出 × 出
  上下文 += 增长
```

重放里的对话按你当时真实的增长来长，只是压缩发生的位置换成了 T。你自己当时的压缩不算增长，上下文从原来的地方接着长。

### 第三步：把各类 token 折成同一种

「读、写、出」是缓存读、缓存写、输出各相当于几个普通输入 token：

| | 缓存读 | 缓存写 | 输出 |
|---|---|---|---|
| Anthropic 模型 | 0.1 | 1.25（缓存保留一小时的 2） | 5 |
| 其他模型 | 0.1 | 1 | 8 |

Pi 的会话记了每次调用的费用，所以 Pi 按这个模型实际的价钱算：缓存读每 token 的价钱 ÷ 普通输入每 token 的价钱，其余同理。不计费的订阅算不出来，就用上表。Claude Code 的会话没有费用，用上表的 Anthropic 一行；一半以上的缓存写是保留一小时的，缓存写按 2 算。

按 API 计费和按订阅额度计，都是按这样加权的 token 数扣的，所以两种情况都适用。

### 第四步：在哪些点之间挑

候选点每 1 万一档。

- **下限**取下面两者中较大的：
  - Pi 5 万，Claude Code 10 万（它的设置不接受更小的值）；
  - 压缩后 + max(压缩后的一半, 20 次调用的增长)，再向上取整到 1 万（Claude Code 比的是设定值，再加 3.3 万）。离摘要太近会刚压完又要压。
- **上限**：Pi 是「窗口 − 16384」（再高，最后一次回复可能装不下）；Claude Code 是窗口，最多 100 万。

「设定值」和「真正压缩的地方」不一定相同：Pi 的设定就是压缩点；Claude Code 的设定是 `autoCompactWindow`，它在设定值减约 3.3 万时压缩，重放时也按这个位置算。

**现在的设定**按设置文件读。设置里什么都没写时，Claude Code 用它自己给模型调的值，插件不知道具体是多少：见过 3 次以上压缩，就用压缩前的中位数加 3.3 万估算；否则按窗口算。

### 第五步：挑点

1. 算出每个候选点的总成本，找到最低的。
2. 成本比最低值高不到 1% 的点里，取最大的那个。压缩越少，丢掉的上下文越少，而这一点成本模型算不进去。
3. 如果量到了压缩耗时：只在「压缩不比现在频繁」的点里挑。先找其中最便宜的，再在比它贵不到 3% 的点里取压缩次数最少的（一样多时取大的）。token 和秒没有共同单位，不拿一个猜出来的汇率去换算，所以宁可不建议让你等更久的点。
4. 比现在的设定省不到 3%，就建议保持现在的设定。
5. 一个模型少于 50 次调用不给建议。

### 没有算进去的

- **压缩丢掉的信息**：只算了「再读回来」的 token，没算 agent 忘掉之前的决定、走回头路这种质量损失。第五步第 2 条偏向较大的点，就是为了抵一点这个。
- **假设对话照原样增长**：换一个压缩点，agent 后面的行为其实也会变，重放只能假设增长和原来一样。
- **摘要大小当成常数**：用的是压缩后的中位数。
- **长上下文让每次调用变慢**：只算了压缩本身的等待，没算上下文长了之后首个 token 来得更慢。
- **Claude Code 的窗口是推出来的**：会话里没记窗口，用过超过 200K 的提示词就按 1M 算。

结果只对你和这个模型成立。用法变了（换了任务类型、换了模型），重新分析一次。

## 怎么跑的

插件脚本跑在 smelt 的 UI 线程上，几百 MB 的会话文件不能在那里读。重活在子进程里做：smelt 自带的 `~/.smelt/bin/smelt-pi` 是 Bun 编出来的，带上 `BUN_BE_BUN=1` 就是一个 Bun，插件用它跑 `engine/cli.js`，读它一行行输出的 JSON。不需要另装 Node 或 Bun。

Pi 各模型的窗口取自 `smelt-pi --list-models`（Pi 判断压缩用的就是这份），`~/.pi/agent/models.json` 里有精确 `contextWindow` 的以它为准。

插件自己的数据在 `~/.smelt/plugin-data/com.smelt.compaction-tune/state.sqlite3`：每个会话文件读出的调用（大小和修改时间没变就不重读），和插件写过哪些设置。

## 安装

需要带「面板插件」设置页的 smelt，用过 Pi（`~/.smelt/bin/smelt-pi` 已经装好，引擎靠它跑）。暂时只支持 macOS 和 Linux。

```bash
git clone https://github.com/smelt-ai/smelt-plugin-compaction
```

打开 smelt 的 **设置 → 通用 → 面板插件**，点「导入插件目录」选这个目录，插件会出现在右侧 Tool Panel（`Opt+Cmd+B`）。边改边看就建软链：

```bash
ln -s "$PWD/smelt-plugin-compaction" ~/.smelt/plugins/compaction-tune
```

## 开发

```
main.js            界面：起引擎子进程、画结果
format.js          界面上的数字和说法
engine/cli.js      引擎入口（Bun）：analyze / apply / undo
engine/agents.js   各 agent 的适配器：会话在哪、窗口、压缩点设在哪
engine/tune.js     重放和挑点
engine/pi.js       读 Pi 的会话文件
engine/claude.js   读 Claude Code 的会话文件、它的压缩点设置
engine/windows.js  模型窗口
engine/pi-settings.js  Pi 设置里的压缩点
engine/store.js    插件的 SQLite（bun:sqlite）
```

不碰界面和 `bun:sqlite` 的模块用 Node 测：

```bash
node --test tests/
```

单独跑引擎：

```bash
BUN_BE_BUN=1 ~/.smelt/bin/smelt-pi engine/cli.js analyze --home ~ --smelt-pi ~/.smelt/bin/smelt-pi
```

插件的 `console.log` 和脚本错误写在 `~/.smelt/app.log`，带 `[plugin]` 标记。
